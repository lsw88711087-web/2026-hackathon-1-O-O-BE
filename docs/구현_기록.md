## 2026-08-12 · 기반 세팅 `4f08265`

### 무엇
Django 5.1 + DRF 프로젝트 골격, 도메인 앱 6개, 모델 전체, 공통 에러 포맷, visit_token 인증, Swagger.

### 왜 필요한가
이후 모든 기능이 이 위에 올라간다. 특히 **인증 방식과 에러 형식은 나중에 바꾸면 프론트가 전부 깨지므로** 첫 커밋에서 확정해야 했다.

### 설계 판단

**SQLite를 쓰되 WAL을 켰다.**
SQLite는 쓰기가 DB 전체를 잠근다. 리포트 워커(백그라운드 스레드)가 도는 동안 `/events` 배치가 들어오면 `database is locked`가 난다. WAL + `timeout=20` + `transaction_mode=IMMEDIATE`로 읽기·쓰기가 서로를 막지 않게 했다.
- 버린 대안: Postgres — 운영이 안전하지만 팀이 SQLite로 결정했다. 대신 아래 두 가지로 보완했다.
- 파생 대응 1: **분석 축 8개를 JSON이 아니라 컬럼으로** 뒀다. SQLite는 JSON 내부 값으로 group by·집계하기가 매우 아프고, `/admin/cohorts`가 색상·소재별 분포를 뽑아야 한다.
- 파생 대응 2: 워커는 계산을 모두 끝낸 뒤 **저장 한 번만** 트랜잭션으로 감싼다(구현 예정).

**`AUTH_USER_MODEL`을 건드리지 않았다.**
사용자는 로그인하지 않고 관리자만 로그인한다. 매장이 하나로 고정이라 브랜드 격리 대상도 없다. 커스텀 유저 모델을 세울 실익이 없어서 Django 기본 `User`를 관리자 계정으로 쓴다.
- 버린 대안: `AdminUser` 커스텀 모델 — 처음엔 명세에 있었지만 "매장 1개 고정"을 반영하면 불필요하다고 판단해 만들지 않았다. `Visitor`(익명)와 이름이 겹치지 않는 부수 효과도 있다.

**Celery를 걷어냈다.**
계약이 요구하는 건 "`/finish`는 즉시 202, 워커가 나중에 `status: ready`"뿐이다. `redis + worker + beat` 3개 프로세스는 얻는 것 없이 데모에서 죽을 지점만 늘린다. `threading.Thread`로 충분하다.

**에러 형식을 한 곳에서 통일했다.**
프론트가 엔드포인트마다 다른 에러 모양을 파싱하지 않게 하려고 커스텀 예외 핸들러를 뒀다. 구현 중 DRF 기본 동작 두 개가 명세와 충돌해서 우회했다.
- DRF 내부 코드(`authentication_failed` 같은 소문자)가 프론트로 새어나가는 문제 → **UPPER_SNAKE code만 신뢰**하고 나머지는 상태코드로 매핑
- `AuthenticationFailed`를 쓰면 `WWW-Authenticate` 헤더가 없을 때 **401을 403으로 강등** → 자체 `Unauthorized` 예외를 만들어 우회
- URL 자체가 안 맞으면 DRF를 타지 않아 HTML이 나가는 문제 → `handler404`/`handler500`도 같은 JSON 형식으로

**`visit_token`은 JWT가 아니라 DB 토큰.**
관람 중 토큰이 만료돼도 **같은 토큰을 그대로 이어 쓸 수 있어야** 한다(이탈 복구). JWT면 만료 복구가 불가능하고 강제 무효화도 안 된다. 요청당 조회 1회가 늘지만 그 대가로 이어하기가 성립한다.

### 검증
`check` 0 issues · 마이그레이션 5개 적용 · `PRAGMA journal_mode` → `wal` 실측 · 401/400/404 응답 형식 실측 · Swagger 200.

### 영향
`AUTH_USER_MODEL`·DB 엔진·에러 형식은 이후 변경하지 않는다. 바꾸면 팀 전체가 깨진다.

## 2026-08-12 · 관리자 로그인 `POST /admin/auth` `4f08265`

### 무엇
브랜드 담당자용 JWT 발급. 기본 `User` + simplejwt.

### 왜 필요한가
B2B 대시보드가 수익 모델의 핵심이고, `/admin/*`은 Bearer 인증이 필요하다. 그 토큰을 받는 창구가 없으면 대시보드를 시작할 수 없다. **기반 세팅 단계에서 함께 만든 이유**는 성공/실패 케이스를 실제로 호출해봐야 공통 에러 포맷을 검증할 수 있었기 때문이다.

### 설계 판단
- 사용자 인증과 **완전히 분리**했다. `authentication_classes = []` + `AllowAny`로 두고 자체 검증만 한다. 사용자 API의 visit_token 흐름과 섞이면 구멍이 생긴다.
- `store_ids`는 고정 매장 하나를 그대로 반환한다. 매장 다중화는 스코프 밖이다.
- 무차별 대입 방지로 `10/min` throttle을 붙였다. 인증·권한은 해커톤이라도 깎지 않는다.

### 검증
정상 200 · 잘못된 비밀번호 **401 `UNAUTHORIZED`** · 이메일 형식 오류 400 + 필드별 detail.

## 2026-08-12 · 입장 API `POST /enter` + 이어하기 `d611001`

### 무엇
익명 UUID 확인·발급, Visit 생성, 전시존·상품 목록 반환, **진행 중 Visit 이어받기**.

### 왜 필요한가
프론트의 첫 화면이 이 응답 하나로 그려진다. 그리고 익명 UUID를 쓰는 이유의 절반이 여기 있다 —
사용자가 **"관람 끝"을 누르지 않고 창을 닫는 일이 흔하다.** 그때 새 Visit을 만들면 아까 본 상품은 Visit A, 지금 보는 건 Visit B에 쌓여서 **리포트가 반쪽짜리**가 되고 채팅 문맥도 끊긴다.

### 설계 판단

**왕복을 늘리지 않았다.**
`POST /enter` 하나가 판정까지 한다. 진행 중 Visit이 있으면 그걸 그대로 돌려주고 `resumed: true`를 실어준다. 프론트는 그 플래그로 모달을 띄우고, "새로 시작"만 `force_new: true`로 재호출한다.
- 버린 대안: `GET /enter/preview`로 먼저 확인 후 입장 — 왕복이 2회가 되고, 그 사이 상태가 바뀔 수 있다.

**이어할 때 같은 토큰을 그대로 반환한다.**
클라이언트가 저장해 둔 토큰이 계속 유효해야 화면 복구가 매끄럽다. DB 토큰을 고른 결정이 여기서 값을 한다.

**만료를 배치가 아니라 조회 시점에 계산한다.**
`find_resumable()`이 미종료 Visit들을 훑으면서 이어받을 것 하나만 남기고 나머지를 그 자리에서 닫는다(`ended_at` 기록, **리포트는 만들지 않음**). 판정 시점이 입장 한 곳뿐이라 스케줄러를 띄울 이유가 없다.
- 버린 대안: `close_stale_visits` 주기 태스크 — beat 프로세스가 하나 더 필요하고, 상태가 두 곳에서 갈라진다.

**깨진 UUID 헤더는 400이 아니라 새로 발급한다.**
오타·저장소 손상으로 400을 주면 입장 자체가 막혀 서비스를 못 쓴다. 위조로 얻을 이익도 없다(남의 Visit을 이어받으려면 추측 불가한 UUID를 정확히 알아야 한다).

**연령대·성별은 새로 시작할 때만 반영한다.**
이어하기에서 덮어쓰면 이미 답한 사람에게 다시 묻는 화면이 필요해진다. 건너뛰기도 허용하므로 값이 없으면 그대로 둔다.

**`store_enter`·`visit_start` 이벤트는 서버가 만든다.**
프론트도 보내면 퍼널의 분모가 두 배가 된다. 생성 주체를 서버 하나로 못 박았다.

**`scenes`는 좌표·도면을 주지 않는다.**
맵 UI는 프론트 자산이다. 서버는 "어느 전시존에 어떤 상품이 속하는지"만 준다. 대신 `no`(번호)를 함께 줘서 **챗봇이 "3번 진열대 2번 상품"으로 안내**할 수 있게 했다.

### 검증
8개 케이스 실측 — 신규 입장 / 이어하기(**visit_id·token 동일**) / `force_new` / 이전 Visit 만료(리포트 없음) / 31분 초과 시 이어하기 거부 / 잘못된 `age_band` 400 / 깨진 UUID 200 + 재발급 / 빈 바디 200.
쿼리 10개, **전시존·상품 각 1쿼리로 N+1 없음**(`prefetch_related`).

### 영향
프론트 계약 변경 2건 — 요청에 `force_new`, 응답에 `resumed`·`resumed_visit` 추가. 이어하기 모달이 필요하다.

## 2026-08-12 · 상품 상세 `GET /products/{id}` + Swagger Authorize `232604b`

### 무엇
상품 상세 조회, Swagger UI의 Authorize 버튼에 `X-Visit-Token` 등록, 토큰 누락 시 401 수정.

### 왜 필요한가
팀원이 직접 API를 눌러보려면 토큰을 넣을 곳이 있어야 한다. Swagger Authorize를 붙이려 했더니
**스키마에 보안 스킴이 안 잡혔다** — `X-Visit-Token`을 소비하는 엔드포인트가 하나도 없었기 때문이다. 그래서 다음 순서였던 상품 상세를 함께 구현했다. 토큰을 테스트할 대상이 필요했다.

### 설계 판단
- `generics.RetrieveAPIView`를 썼다. 표준 조회라 `APIView`로 내려갈 이유가 없다.
- 응답에서 **`llm_context`와 분석 축 8개를 제외**했다. 프론트가 쓸 일이 없고, 챗봇 프롬프트 내용이 노출되면 안 된다. 필드를 명시해서 잠갔다(`fields='__all__'` 금지).
- `preset_answers`를 상세 응답에 함께 내려준다. 프리셋 버튼은 LLM이 아니라 미리 작성한 문구라서, 상품을 열는 순간 이미 손에 있어야 즉시 뜬다.
- `VisitTokenScheme`을 인증 클래스와 **같은 파일에** 뒀다. drf-spectacular는 import된 확장만 등록하는데, 이 모듈은 `DEFAULT_AUTHENTICATION_CLASSES` 때문에 기동 시 항상 로드된다.

### 검증 중 발견한 버그
**토큰 누락이 403 `FORBIDDEN`으로 나갔다.** 명세는 누락·만료·위조를 모두 401 `INVALID_VISIT_TOKEN`으로 정의한다. 원인은 DRF가 인증 정보 없을 때 401을 403으로 강등하는 동작이었다. 퍼미션에서 `False`를 반환하는 대신 `InvalidVisitToken`을 직접 던져 고쳤다.
- 종료된 Visit은 별개다. 토큰 자체는 유효하므로 401이 아니라 403이며, **상품 조회는 막지 않는다**(읽기는 허용).

### 검증
정상 200 · 토큰 누락 401 · 위조 토큰 401 · 없는 상품 404 · **내부 필드 유출 0건**(응답 키 9개 확인).

## 2026-08-12 · 행동 이벤트 수집 `POST /events`

### 무엇
프론트가 모아 보낸 행동 이벤트 배치를 append-only로 저장. 멱등 처리, 체류시간 상한, 참조 검증.

### 왜 필요한가
리포트 분석의 **원재료**가 여기서 들어온다. 이게 없으면 취향 벡터를 만들 재료가 없고 대시보드 지표도 전부 빈다. 매 클릭마다 서버를 치지 않고 모아 보내는 이유는 **브라우저가 닫혀도 직전 기록이 남게** 하려는 것이다(주기 전송 + `beforeunload`).

### 설계 판단

**`accepted`/`duplicated`를 정확히 세려고 저장 전에 한 번 조회한다.**
`bulk_create(ignore_conflicts=True)`는 몇 건이 무시됐는지 알려주지 않는다(SQLite에서는 PK도 안 돌려준다). 그래서 기존 `event_id`를 미리 조회해 계산했다. 조회 1회로 끝나고 배치 크기와 무관하다.
- 버린 대안: 건별 `get_or_create` — 50건이면 쿼리 100개. SQLite 쓰기 잠금까지 겹쳐 최악이다.

**배치 내부 중복도 걸러낸다.**
프론트 재시도 로직이 같은 배치를 이어붙이면 한 요청 안에 같은 `event_id`가 두 번 들어올 수 있다. DB 유니크 제약으로도 막히지만 그러면 `accepted` 수가 틀리게 나온다.

**없는 `scene_id`/`product_id`는 400으로 막았다.**
프론트는 `/enter`가 내려준 목록에서 id를 얻으므로 모르는 id가 오면 코드 버그다. 조용히 NULL로 저장하면 **분석 수치가 눈에 안 보이게 틀어진다.** 어떤 id가 문제인지 `detail`에 담아 프론트가 바로 고칠 수 있게 했다.
- 트레이드오프: 배치 하나가 통째로 거부된다. 다만 이벤트는 멱등 재전송이 전제라 데이터가 유실되지는 않는다.

**서버 전용 타입 3종은 버리고 `ignored`로 알려준다.**
`store_enter`·`visit_start`·`visit_end`는 서버가 만든다. 프론트도 보내면 퍼널의 분모가 두 배가 된다. 400으로 막으면 나머지 정상 이벤트까지 날아가므로, 버리되 **몇 건 버렸는지는 응답에 남겼다.** 조용히 사라지면 프론트가 자기 버그를 못 찾는다.
- 계약 변경: 응답에 `ignored` 필드 추가(기존 `accepted`/`duplicated`는 그대로).

**`dwell_ms`는 서버에서 5분으로 자른다.**
탭을 백그라운드에 두면 30분이 찍힌다. 체류시간은 관심도 계산에서 가장 큰 가중치를 갖는 신호인데, 검증 없이 믿으면 취향 프로필이 한 상품에 끌려간다. 클라이언트 값은 신뢰 경계 밖이다.

**클라이언트가 보낸 `visit_id`를 믿지 않는다.**
토큰이 가리키는 방문과 다르면 403이다. 남의 방문에 이벤트를 심으면 그 사람의 리포트가 오염된다.

**종료된 Visit에는 쌓지 않는다(`IsOpenVisit` → 403).**
퇴장 후 들어오는 이벤트를 받으면 이미 박제된 리포트와 원본이 어긋난다.

### 검증
11개 케이스 실측 — 정상 3건 202 / 재전송 `duplicated:3` / **`dwell_ms` 1800000 → 300000** / 배치 내부 중복+서버 전용 혼합 시 `accepted:1 duplicated:1 ignored:2` / 없는 product 400 + id 표시 / 남의 visit_id 403 / 토큰 없음 401 / 없는 event_type 400 / **50건 배치가 쿼리 7개**(건수 무관) / `last_seen_at` 갱신 / 종료된 Visit 403.

### 영향
`last_seen_at`을 여기서 갱신하므로 **이벤트를 주기적으로 보내는 동안 이어하기 30분 타이머가 계속 연장된다.** 관람 중에 만료되지 않는다는 뜻이다.

## 2026-08-12 · 구현 전수 점검에서 발견한 5건 수정

명세·기획과 코드를 다시 대조하면서 "동작은 하지만 나중에 터지는" 것들을 찾았다.

### ① CORS 허용 헤더가 기본 목록을 덮어쓰고 있었다 (가장 위험)
`CORS_ALLOW_HEADERS`에 4개만 나열해서 django-cors-headers의 기본값(`accept`·`origin`·`x-requested-with`·`x-csrftoken` 등)이 **전부 사라졌다.** 프론트가 붙는 순간 브라우저 preflight가 거부될 수 있었고, 백엔드 단독 테스트(curl)로는 절대 드러나지 않는다. `default_headers`를 펼친 뒤 커스텀 두 개를 더하는 방식으로 고쳤다.

### ② `dwell_ms`에 문자열이 들어와도 저장됐다
`'아무문자열'`이 그대로 `metadata`에 저장됐다. 저장은 성공하고 **나중에 워커가 합산할 때 터진다.** 가장 나쁜 형태의 버그다. 시리얼라이저에서 0 이상 정수만 받도록 막았다. 음수(`-5000`)도 같이 막았다 — 관심도 계산을 왜곡한다.
- 상한(5분) 처리는 서비스에 남겼다. 형식 검증은 입구에서, 정책은 안에서.

### ③ 대상 없는 이벤트가 통과했다
`product_id` 없는 `product_view`가 201로 저장됐다. 저장은 되지만 **분석에서 조용히 사라진다.** 지표가 틀렸는데 아무도 모르는 상태가 된다. 타입별 필수 대상을 시리얼라이저에서 검증한다.
- `scene_*`·`hotspot_click` → `scene_id` 필수
- `product_*`·`recommendation_click` → `product_id` 필수
- `chatbot_open`·`question_submit`·`recommendation_impression`은 대상이 없어도 의미가 있어 그대로 둔다

### ④ 배치 크기 상한이 없었다
프론트 재시도가 겹치면 수만 건이 한 요청으로 올 수 있다. SQLite 쓰기 잠금까지 겹치면 서버가 멈춘다. `EVENT_BATCH_MAX = 200`으로 제한했다.

### ⑤ 시드의 축 검사가 2개만 보고 있었다
`_products_missing_axes()`가 `category`와 `mood`만 확인했다. 이름은 "축 누락 검사"인데 8개 중 2개만 봤다. 크롤링 데이터 30개를 넣을 때 **누락을 못 잡으면 그 상품이 분석에서 사라진다.** 8개 전부 검사하도록 고쳤다.

### 검증
새 케이스 5개(문자열 dwell / 음수 dwell / 대상 없는 product_view / 대상 없는 scene_view / 201건 배치) 전부 400 + 필드별 메시지. 기존 경로 회귀 확인 — `/enter` 200, 이어하기 `resumed:true`, `/products` 200, `/admin/auth` 200, `/django-admin/` 302, `/api/schema/` 200.

## 2026-08-12 · 채팅 액션 메시지 기록 `POST·GET /chat/messages`

### 무엇
클릭을 말풍선으로 적립하고 타임라인을 복원한다. 진열대·상품 클릭, 프리셋 열람, 챗봇 첫 인사, `current_context` 계산.

### 왜 필요한가
**이 API가 O&O의 차별점을 지탱한다.** 채팅창이 빈 화면에서 시작하지 않고, 매장을 돌아다닌 행적이 이미 쌓여 있다. 그래서 "채팅으로 대화하기"로 넘어갔을 때 사용자가 **상품명을 말하지 않아도** AI가 어떤 상품 얘기인지 안다.
그리고 이 기록이 리포트 분석(AI ②) ③′단계의 입력이다. 직전까지 `chat_logs`가 0건이라 AI 두 지점 모두 재료가 없었다.

### 설계 판단

**표시 문구를 서버가 만든다** (명세 요구사항).
클라이언트는 `type` + 대상 id만 보낸다. 클라이언트가 보낸 문장은 그대로 AI 프롬프트에 들어가므로 신뢰 경계 밖이다. 브랜드 문구 통제와 표현 일관성도 함께 얻는다.

**직전과 같은 클릭은 쌓지 않고 `200`으로 기존 메시지를 돌려준다.**
같은 상품을 연속으로 누르면 화면이 같은 말풍선으로 도배된다. 다만 **수치는 잃지 않는다** — 조회 횟수는 `POST /events`가 따로 남기고, 프론트는 클릭 한 번에 두 API를 모두 호출한다. 역할 분리가 여기서 값을 한다.
- 중복 판정은 **직전 `user_action`의 문구 비교**로 한다. 액션 타입을 별도 컬럼으로 저장하지 않아도 되고(마이그레이션 불필요), "진열대1 → 상품A → 진열대1"처럼 돌아온 경우는 문구가 달라 정상적으로 쌓인다.
- **프리셋은 중복 제거 대상에서 뺐다.** 같은 걸 다시 물어보는 것 자체가 의미 있는 행동이다.

**프리셋 열람은 말풍선 2개를 만든다.**
누른 버튼(`user_action` "가격") + 미리 작성된 답변(`preset`). 답변만 남기면 타임라인이 "갑자기 가격 얘기가 나오는" 것처럼 읽힌다. 응답으로는 답변 쪽을 돌려준다 — 버튼 라벨은 프론트가 이미 안다.
- 프리셋 문구가 비어 있으면 폴백 문장 + `logger.warning`. 데모 중 화면이 깨지는 것보다 낫고, 누락은 `seed_demo` 검사로도 잡는다.

**챗봇 첫 인사를 서버가 입장 시 적립한다.**
프론트 하드코딩이 아니라 DB에 넣는 이유: `GET /chat/messages` **하나로 화면이 완전히 복원**돼야 한다. 이어하기로 돌아왔을 때도 인사가 제자리에 있다.

**`current_context`는 상품만 클릭해도 `scene_id`를 채운다.**
가장 최근 상품이 속한 존으로 보완한다. 챗봇이 "3번 진열대 2번 상품"처럼 번호로 안내해야 하므로 존 정보가 비면 안 된다.

**읽기와 쓰기의 권한을 다르게 뒀다.**
`POST`는 진행 중 관람만(`IsOpenVisit`), `GET`은 종료된 관람도 허용한다. 퇴장 후 리포트를 기다리는 동안에도 대화를 볼 수 있어야 한다.

**멱등 키를 추가하지 않았다.**
명세에 없고, 이 API는 화면·문맥용이다. 재전송으로 말풍선이 하나 중복돼도 분석 수치는 `/events`가 담당하므로 데이터가 망가지지 않는다. 프론트에 "실패 시 재시도 불필요"를 안내한다.

### 검증
시안 흐름 재현 — 진열대 클릭 201 → 같은 진열대 재클릭 **200(중복 무시)** → 상품 클릭 201 → 프리셋 `price` 201 → 같은 프리셋 다시 201(반복 허용) → 프리셋 `material` 201 → 상품 본 뒤 진열대 재클릭 201(문구가 달라 정상 적립).
복원 결과가 시안과 동일(인사 → 진열대 → 상품 → 가격/답변 → 재질/답변). `current_context` = `{sc_01, p_101}`.
실패 케이스 7개 — 없는 `type` 400 · `scene_id` 누락 400 · 없는 상품 400 · `preset_key` 누락 400 · 잘못된 `preset_key` 400 · 남의 `visit_id` 403 · 토큰 없음 401.
이어하기 후 타임라인 복원 확인(인사 포함) · 종료된 관람 GET 200 / POST 403.

### 설계 판단

**클라이언트는 문맥을 보내지 않는다.**
서버가 `chat_logs`에서 최근 12개 메시지와 마지막으로 클릭된 상품을 읽어 프롬프트를 만든다. 그래서 "이 상품의 디자이너 의도를 설명해줘"가 상품명 없이 동작한다. `context`를 명시로 보내면 그게 우선한다(명세 요구사항).

**클릭 기록(`user_action`)도 프롬프트에 넣는다.**
"1번 진열대 클릭 → OO 상품 클릭 → 가격" 흐름이 그대로 대화 이력이 되므로 OpenAI 메시지에서는 `user` 역할로 매핑했다. 프리셋 답변은 `assistant`로 넣는다 — 챗봇이 이미 한 말이기 때문이다.

**LLM 접점을 `common/llm.py` 하나로 묶었다.**
앱 코드는 OpenAI SDK를 import하지 않는다. 모델명은 `.env`의 `OPENAI_MODEL`로 빼서 교체 지점을 한 곳으로 만들었고, 키가 없으면 원인을 명시한 예외를 던진다(데모 중 조용히 실패하는 게 최악이다).

**답변은 스트림이 끝난 뒤 한 번에 저장한다.**
조각마다 UPDATE를 치면 SQLite 쓰기 잠금이 스트리밍 도중에 걸린다.

**LLM 실패를 SSE 이벤트로 보낸다.**
스트림이 시작된 뒤에는 HTTP 상태를 바꿀 수 없다. `data: {"error": {...}}`를 흘려보내 프론트가 그 자리에 안내를 띄울 수 있게 했다.

**throttle을 방문 단위로 셌다.**
DRF 기본 `SimpleRateThrottle`은 IP를 쓰는데, 매장 와이파이를 함께 쓰는 손님 전체가 한 사람으로 묶여 서로의 한도를 잡아먹는다. `visit.id`를 키로 바꿨다.

### 검증 중 발견해서 고친 것
첫 라이브 테스트에서 "디자이너 의도를 설명해줘"에 **"제공된 정보에 없습니다"** 라는 답이 나왔다. 프롬프트에 `llm_context`와 분류 축만 넣고 **`story`와 `preset_answers`를 빼먹었기 때문**이다. 정작 그 답이 거기 있었다.
- 상품에 대해 서버가 아는 사실을 전부 넣도록 고쳤다. 특히 **프리셋 문구는 브랜드가 직접 작성한 문장이라 근거로 삼기에 가장 안전하다.**
- 고친 뒤: "1976년 뮌헨의 여행 가방 실루엣을 현대적으로 재해석해 디자인되었습니다" / "코팅 캔버스에 레더 트리밍으로 생활 방수가 가능합니다. 마른 천으로 닦아 주시면 됩니다"

## 2026-08-13 · 챗봇 트리거 로직 구현 (뮤즈 · 추상→구체)

### 무엇
관찰 → 가설 → Y/N → 분기 루프. 축 계산(`analysis/taste.py`), 추천(`analysis/recommend.py`), 트리거 6종(`chat/triggers.py`), 응답 처리(`chat/answers.py`), 어휘 사전(`chat/taste_map.py`), 손님용 표현(`chat/wording.py`).

### 왜 필요한가
"좋아하는 색이 뭐예요?"는 설문이고, "블랙 위주로 보셨네요, 색은 이쪽이 편하세요?"는 대화다. 매장에서 서 있는 손님에게 타이핑을 요구하지 않고 버튼 한 번으로 취향을 확정받는다. 그리고 **축을 묻지 않고 상품을 묻는다** — 상품 하나에 8축이 붙어 있어 "이 백팩 마음에 드세요?" 한 번이 축 8개를 가져온다.

### 설계 판단

**축값은 누적이 아니라 함수다.** `축값 = f(관심 상품 집합, 회피 데이터)`. 같은 입력에서 같은 결과가 나오므로 저장하지 않고, 방문 중 표시와 퇴장 후 워커 확정이 같은 함수를 돈다. **행동 점수 이중 계산 문제가 구조적으로 사라진다.**

**비율 + 표본 축소 + 진영 격차.** 여러 상품의 공통점이 취향이다(비율). 표본 1개가 1.0을 갖지 못하게 `× n/(n+2)`. 유효성은 값이 아니라 **진영 격차**로 본다 — `black 0.3 · navy 0.3 · pink 0.3`을 값 단위로 보면 "색 취향 없음"이 되는데, 무채색을 두 종류 골랐으니 틀린 판정이다.

**저장은 events에 없는 것만.** `TasteProfile.vector`에 `locks`·`spoken`·`avoided`·`confirmed`·`rejected`·`asked`·예산 카운터·`pending`. JSONField라 **마이그레이션 0**이다. `ActionType`에 3종을 추가했지만 API 입력 enum이라 DB가 안 바뀐다.

**`pending`을 저장한다.** 문서에는 "파생 계산"으로 적었지만 구현에서 불가능했다 — 응답이 왔을 때 그게 어느 축·어느 상품을 물은 가설이었는지 알아야 하는데 `chat_logs`에는 문구만 남는다.

**진영 누락을 기동 시 검사한다.** `analysis.E001` system check. 축 값이 어느 진영에도 없으면 그 값을 고른 손님이 **조용히 반대 진영으로 분류**된다 — 에러 없이 결과만 틀리는 종류다.

### 구현하며 잡은 결함 8개

| # | 결함 | 왜 위험한가 |
| --- | --- | --- |
| 1 | **`cognac`이 진영에 없었다** | 코냑을 많이 본 손님이 "눈에 띄는 색"으로 판정됐다. 위 system check를 만든 계기 |
| 2 | **집합 1개로 4축 전부 유효** | 유효성이 비율만 보므로 상품 하나로 유형이 확정된다 → 최소 집합 크기 3 (lock 면제) |

| 8 | **같은 축이면 부정을 지웠다** | `"미니멀은 좋고 볼드는 싫다"`는 정합한 진술인데 축 단위로 지워 부정이 사라졌다 → 같은 축 + 같은 값일 때만 |

7·8은 **정반대 해석**이 나가는 결함이었다. 사전 매칭은 LLM 없이 도는 경로라 여기가 틀리면 조용히 반대 추천이 나간다.

### 검증

## 2026-08-18 · 배포 준비 (가비아 VM)

### 무엇
`deploy/` 디렉터리(nginx·systemd·백업·가이드)와 배포용 설정을 추가했다. 서버를 받기 전에 미리 만들어, 받은 날 30분 안에 올릴 수 있게 하는 것이 목적이다.

### 왜 HTTPS가 협상 불가인가
프론트가 Netlify(HTTPS)에 올라간다. HTTPS 페이지에서 HTTP API를 부르면 브라우저가 mixed content로 차단한다. 즉 **인증서가 없으면 연동 자체가 0%**다.

도메인 구매 없이 인증서를 받기 위해 `sslip.io`를 쓴다(IP를 도메인처럼 해석해주는 공개 DNS). Let's Encrypt의 HTTP-01 검증이 통과한다.

**버린 대안**: Netlify의 `/api/*` 프록시 리다이렉트. 같은 오리진이 되어 CORS가 사라지는 매력이 있지만 **Netlify 프록시는 응답을 버퍼링하고 타임아웃이 짧다** — 챗봇 SSE가 죽는다.

### 발견한 블로커 2건
- **`STATIC_ROOT` 미설정** → `DEBUG=False`에서 `collectstatic` 실패 → `django-admin` CSS 깨짐. 상품 30개를 admin으로 입력할 계획이라 실제 장애다.
- **미디어 미서빙** → `config/urls.py`가 `DEBUG`일 때만 미디어를 붙인다. 배포에서는 nginx `location /media/`가 담당한다.

whitenoise를 쓰지 않은 이유: nginx가 어차피 앞에 서므로 static을 nginx에서 주면 된다. 의존성을 하나 더 늘릴 이유가 없다(미디어는 whitenoise가 다루지도 않는다).

### 프록시 뒤에서 필요한 설정
- `SECURE_PROXY_SSL_HEADER` — nginx가 TLS를 끊으므로 없으면 Django가 자기를 http로 착각해 Swagger 서버 주소와 미디어 URL이 http로 나간다(= mixed content).
- `CSRF_TRUSTED_ORIGINS` — https `django-admin` 로그인에 필요.
- `SESSION_COOKIE_SECURE`/`CSRF_COOKIE_SECURE`는 `not DEBUG`에 묶었다. 상수 `True`로 두면 로컬 http admin 로그인이 막힌다.
- `CORS_ALLOWED_ORIGIN_REGEXES` — Netlify PR 미리보기는 `deploy-preview-3--사이트.netlify.app`처럼 주소가 매번 다르다. 고정 목록만으로는 미리보기에서 API가 전부 막힌다.

### nginx에서 지우면 안 되는 것
`proxy_buffering off` + `proxy_cache off`. 켜져 있으면 nginx가 SSE를 다 모았다가 한 번에 보내 스트리밍이 무의미해진다. 코드의 `X-Accel-Buffering: no`만 믿으면 안 된다.

### 워커 1개인 이유
리포트 생성이 `threading.Thread`이고 DB가 SQLite다. SQLite는 쓰기가 DB 전체를 잠그므로 프로세스를 늘리면 쓰기 경합만 커진다. 2vCore·데모 트래픽에는 1개로 충분하다.

### 일정 리스크
서버 생성 가능일 **8/18 = 개발 마감일**, 기술지원 종료 **8/21 18:00**, 삭제 **8/28 23:59(중커톤 당일)**. 마감일에 배포까지 몰면 둘 다 터진다 → 8/18 오전에 뼈대만 먼저 올려 프론트에 주소를 넘기고, 이후 코드는 `git pull`로 갱신한다. 데모 직후 `deploy/backup.sh`로 DB·미디어·`.env`를 받아둔다(서버는 통보 없이 삭제된다).

### 검증
`DEBUG=False` 실서버 기동 — `collectstatic` 163개 성공(`staticfiles/admin/css/base.css` 확인), Swagger 200, `/enter` 200, `django-admin` 302. CORS 정규식은 `deploy-preview-3--oando.netlify.app`에 허용 헤더가 나가고 `evil.example.com`에는 나가지 않는 것까지 확인.

## 2026-08-18 · 화보 대응 ①② — 토큰 규약 변경 + `/enter` 확장

### 무엇
v0.6 화보 명세의 착수 순서 1·2번. 화보 API를 만들기 전에 **전 구간이 선행으로 걸려 있던 두 가지**를 먼저 걷어냈다.

### ① 토큰은 왜 "퇴장 시 만료"를 버렸나

기존 만료 조건은 두 개였다 — `/finish` 호출 즉시, 그리고 진입 후 일정 시간. 그런데 **화보와 재생성이 전부 `/finish` 이후에 일어난다.** [다시 돌리기]는 화보가 완성된 그 화면의 버튼인데, 기존 규약대로면 그 시점에 토큰이 이미 죽어 있다.

만료 조건을 **진입 후 3시간 하나로** 줄였다. ①이 하던 "리포트 박제 보호"는 `/events` 타입 화이트리스트가 전담한다 — 같은 일을 두 군데서 막고 있었고, 그중 토큰 쪽이 화보를 방해했다.

만료 판정은 인증 시점에 한다(`VisitTokenAuthentication`). 배치를 기다리지 않으므로 사용자 입장에서는 정확히 3시간이다.

**기준 시각을 `last_seen_at`에서 `started_at`으로 바꿨다.** 3시간은 "관람 20분~1시간 + 화보 + 재생성 3회"를 담는 **총 예산**이지 유휴 시간이 아니다. 마지막 활동 기준으로 두면 오래 머무는 사람의 토큰이 무한히 연장된다.

`is_open`(관람 중인가)과 `is_expired`(토큰이 죽었나)를 분리한 것이 이번 변경의 핵심이다. 이전에는 한 값이 두 질문에 답하고 있었다.

### `/events`가 종료된 방문도 받게 된 이유

퍼미션을 `IsOpenVisit` → `IsVisitAuthenticated`로 낮췄다. 화보 이벤트를 받아야 하는 것이 직접적인 이유지만, 원래도 결함이었다 — `/finish` 뒤에 클라이언트가 마지막 배치를 보내면 그대로 401이 나서 **종료 직전 구간이 통째로 유실**된다. 전환 분석에서 가장 중요한 구간이다.

대신 타입으로 가른다. 종료 후에는 `lookbook_*`·`photo_*`만 저장하고 관람 이벤트는 `ignored`로 버린다. 리포트는 `/finish` 시점에 박제되므로 뒤늦게 온 상품 조회는 반영될 수 없고, 그대로 저장하면 원본과 리포트가 서로 다른 말을 하게 된다.

### 배치 상한을 400에서 `rejected`로 바꾼 이유

기존은 200건 초과 시 400이었다. 매장 와이파이가 끊겼다 복구되면 밀린 버퍼가 한 번에 몰리는데, 그때 통째로 거절하면 **유효한 기록까지 같이 날아가고 클라이언트에도 서버에도 흔적이 남지 않는다.**

앞에서부터 200건을 저장하고 나머지 수를 `rejected`로 알려준다. 순서가 보존되므로 클라이언트는 뒤쪽 `rejected`건만 다시 보내면 된다. 메모리 보호용 절대 상한(1000건)은 400으로 남겼다.

`ignored`와 `rejected`를 나눈 기준은 **클라이언트가 재전송해야 하는가**다. 하나로 합치면 프론트가 판단할 수 없다.

### ② `/enter` — 뮤즈 번호와 응답 필드

`muse_no`는 매장 카운터를 올려 발급한다. SQLite에는 `select_for_update`가 없어 `F()` 갱신에 기대는데, 연결이 `transaction_mode=IMMEDIATE`라 트랜잭션 시작 시점에 쓰기 락을 잡는다. 동시 입장 3건에서 N.003/004/005가 나오는 것을 확인했다. 이어하기에서는 재발급하지 않는다 — 뒤로가기 한 번에 번호가 올라가면 안 된다.

`resumed` → `is_resumed`로 이름을 바꾸고 `is_new`를 추가했다. **프론트가 아직 붙이지 않은 시점이라 지금 바꾼다.** 명세 본문 여러 곳이 이 이름을 쓰는데 응답 정의에만 빠져 있어서, 스펙만 보고 구현하면 재진입 분기를 못 만든다.

`anonymous_uuid`를 항상 내려주도록 바꿨다. 신규 발급일 때만 주면, 클라이언트가 보낸 uuid가 죽은 값이라 서버가 새로 발급한 경우 클라이언트는 자기 uuid가 유효하다고 오해하고 **죽은 값을 영원히 계속 보낸다.**

### `age_band`·`gender`를 Visitor → Visit으로 옮긴 이유

같은 사람이 다음 방문에서 다르게 답할 수 있고, 코호트 집계 단위가 방문이다. Visitor에 두면 **마지막 입력이 과거 방문의 집계까지 소급해서 바꾼다.** 명세의 근거를 그대로 따랐다.

### `is_auto_closed`

방치돼서 서버가 닫은 방문과 사용자가 "새로 시작"을 눌러 닫힌 방문은 다르다. 전자만 `True`이고, 평균 체류시간·리포트 완료율의 분모에서 빠진다.

### 검증
실서버 기준. 입장 N.001 → 이어하기에서 번호 유지 → 동시 3건 N.003/004/005 중복 없음. 종료 후 `product_view`는 `ignored`, `lookbook_share`·`photo_capture`는 저장, 섞은 3건은 화보 1건만 통과. `/chat/messages`는 종료 후 403 유지. 250건 배치 → `accepted 200 / rejected 50`. 3시간 1분 경과 토큰 → 401. 2시간 경과는 정상 이어하기(기존 30분 로직이면 만료됐을 건). `force_new`는 `is_auto_closed=False`. 챗봇 스트리밍 회귀 통과(`_describe_visitor`가 Visit을 읽도록 바뀐 경로).

## 2026-08-19 · 챗봇 가드레일 프롬프트 (범위 이탈 · 조작 대응)

### 무엇
`GUARDRAIL_PROMPT`를 추가하고 손님 질문 **바로 앞**에 넣었다. 시스템 프롬프트와 질문 사이가 멀면 앞선 지시가 흐려지고, 조작 문장은 대개 이번 질문 안에 들어온다.

### 범위 정책 — 거절이 아니라 전환, 그리고 3층
"완곡 거절" 하나로 통일하거나 "간단히 답하고 문장 붙이기"로 통일하면 양쪽 다 손해다.

- **1층 매장/상품** → 정상 답변
- **2층 매장으로 이어짐**(스타일·상황·색 조합·선물) → **답한다.** "여행 갈 때 뭐 들고 가?"는 `use_case=travel`을 확정할 수 있는 최고의 질문이다. 거절하면 취향 데이터를 스스로 버린다
- **3층 완전 무관**(시사·의학·법률·계산·코드·타 브랜드 평가) → 답을 시도하지 않고 한 문장으로 전환

용어를 "거절"에서 "전환"으로 바꾼 이유: 큐레이터 페르소나에서 "죄송하지만 답변할 수 없습니다"는 콜센터 말투다. 명품 매장 큐레이터는 거절하지 않고 화제를 옮긴다. 그래서 거절 문구를 **명시적으로 금지**하고 O/X 예시를 넣었다.

### 인젝션 방어 — 프롬프트는 마지막 층이다
이미 프롬프트보다 강한 방어가 셋 있었다. 추천 후보를 서버가 고정(목록 밖 상품 추천이 구조적으로 불가), `llm_context`에 재고·할인 없음(지어낼 재료가 없음), 입력 500자·출력 400토큰(긴 탈선이 잘림).

그 위에 얹은 것 중 실제로 효과가 컸던 건 **출력 형식 잠금**이다. "시·표·목록·코드·JSON으로 답하지 않는다"를 넣자 형식 우회가 통째로 막혔다. 규칙 내용을 직접 물으면 막히지만 "시로 번역해줘"로는 새는 문제가 있었는데, 내용을 지키라고 더 강하게 말하는 대신 **형식을 잠그는 쪽이 통했다.**

그리고 조작 시도에 **설명하지 않게** 했다. "저는 시스템 프롬프트를 공개할 수 없습니다"라고 답하면 공격자에게 힌트를 주고 대화가 그쪽으로 끌려간다.

### 발견한 진짜 결함 — 프롬프트가 아니라 데이터 부재
1차 검증에서 **구찌 가방·버버리 트렌치코트·없는 5번 진열대**가 나왔다. 프롬프트는 "아래 추천 후보에 있는 상품과 번호만 쓰라"고 말하는데, 확인해 보니 **후보 블록이 아예 없었다.**

- 상품 클릭 없이 챗봇을 먼저 열면 `current_context`가 비고 `suggest()`도 빈 배열이다
- 가리킬 목록이 없는 상태에서 "목록에만 있는 것을 쓰라"는 지시는 무의미하다. 모델은 빈칸을 사전지식으로 채운다

**프롬프트 문구를 고치는 대신 데이터를 넣었다.**
- `_describe_store()` — 매장 이름·진열대 번호와 이름·취급 분류를 DB에서 읽어 항상 넣는다. "위에 없는 브랜드·상품·진열대 번호는 이 매장에 없습니다"로 닫는다
- `NO_CANDIDATE_NOTE` — 후보와 상품 문맥이 모두 없을 때만 넣는다

`NO_CANDIDATE_NOTE`의 첫 버전은 **매장 질문을 범위 밖으로 만들어버렸다.** "특정 상품을 지목하지 마세요"만 썼더니 모델이 "답할 수 없음"으로 해석해 소재 질문에 전환 문구를 냈다. "이건 답할 수 없는 질문이라는 뜻이 아니다 / 되묻되 전환 문구를 쓰지 말라"를 명시해 고쳤다.

### N+1
`_describe_store()`가 진열대마다 상품을 다시 조회해 프롬프트 조립에 15쿼리가 들었다. `prefetch_related("products")`로 12쿼리.

### 검증
실서버 + 실제 LLM으로 13발화. 상품 질문(문맥 유/무) · 상황 질문 · 무관 질문 2종 · 인젝션 2종 · 확약 유도 · 타 브랜드 비교 · 감정 · 형식 조작 4종(시·JSON·표·역할변경).

- 다른 브랜드 상품 창작 **0건** (1차에서는 3건)
- 없는 진열대 번호 **0건** (1차에서는 2건)
- 형식 조작 4종 전부 2~3문장 산문 유지
- 감정 발화에 상품·진열대·쇼핑 권유 없음
- 문맥 있는 상품 질문은 실제 `preset_answers` 근거로 정확히 답함

### 남은 것
- 전환 문구가 아직 "그 요청은 제 범위를 벗어나네요" 정도로 약하게 거절 느낌이 남는다. 유출·형식 이탈은 없어 기능적으로는 안전하다. 카피 톤은 기획 확인이 필요하다
- 상품 30개가 들어오면 `_describe_store()`의 취급 분류가 길어질 수 있다. 토큰을 재확인할 것

```
             "dimensions": "약 11 x 25 x 18cm", "size": "S"}
```

그런데 `_describe()`가 `attributes`를 프롬프트에 넣지 않았다. 결과:

- "크기 얼마예요?" → **"매장 직원에게 문의해 주세요"** (DB에 있는데)
- "소재가 뭐야?" → "그레인 레더" (분석 축의 뭉뚱그린 분류. 실제는 "스페인산 엠보스드 레더")
- "무슨 색이야?" → "핑크색" (실제는 "lotus pink")

`attributes`를 프롬프트에 추가해 셋 다 정확해졌다. 분석 축은 집계용이라 값이 거칠고, **사람이 물어보는 구체적인 사실은 `attributes`에만 있다.**

### ② 빈 축이 취향 벡터를 오염시켰다

실데이터는 4~7단(악세서리·의류)의 분류 축이 비어 있다 — **33/63(52%)**. `_ratios()`가 빈 문자열을 하나의 값으로 셌다.

```
color: {'': 0.667}
```

`''`는 어느 진영에도 없어 **유효성 판정에는 영향이 없었다**(그래서 조용했다). 하지만 `TasteProfile.vector`에 그대로 저장되고, 최빈값이 되면 프롬프트와 리포트 문구로 샐 수 있었다.

빈 값을 세지 않도록 고쳤다. **분모는 전체 관심 상품 수로 유지했다** — 근거가 적을수록 비율이 낮게 나와 판정이 보류되는 쪽이 이 프로젝트의 기존 태도와 맞는다. 분모까지 "값이 있는 상품 수"로 바꾸면 상품 하나로 축이 확정되는 역효과가 난다.

## 실상품 60개 적재 · 업로드 백엔드 · 화보 실생성 (2026-08-19)

### 왜 presign URL이 uploads.invalid였나

버그가 아니라 `STORAGE_BACKEND=dev`의 설계된 동작이다. `.invalid`는 RFC 2606이 "절대 존재하지 않는다"고 못박은 예약 도메인이고, **받는 척하면 업로드가 됐다고 착각하게 되므로** 일부러 죽은 주소를 쓴다.

문제는 버킷이 없다는 것이었다. `local` 백엔드를 추가해 Django가 PUT을 직접 받는다. **presign 응답 형식은 s3와 완전히 같게 유지했다** — 프론트가 이미 presign→PUT으로 구현을 마쳤고, 나중에 R2가 생겨도 `.env` 한 줄만 바꾸면 되어야 한다.

버린 대안: multipart 직접 업로드. 프론트 재작업이 필요하고, 원 설계가 피하려던 "사진 바이트가 Django를 지나간다"로 되돌아간다.

**사진은 `MEDIA_ROOT`가 아니라 `uploads/`에 쓴다.** nginx가 `/media/`를 통째로 공개 서빙해서, 거기 두면 명세의 `photos/ 비공개, 워커만 접근`이 깨진다. 얼굴 사진이 키만 알면 열리는 파일이 된다.

서명은 붙이지 않기로 했다(사용자 판단). 그래서 **키 형식 정규식이 유일한 방어선**이다 — `../`나 임의 키로 쓰는 시도가 거기서 끊긴다.

### Redis를 쓰는 이유는 파일에 적용되지 않는다

"폴링 상태 때문에 Redis를 쓰니 파일도 공유가 안 될 것"이라는 추론이 있었으나, Redis가 필요한 이유는 **LocMem이 프로세스별 메모리**이기 때문이다. 디스크는 같은 VM의 모든 gunicorn 워커가 공유하고, 화보 워커는 애초에 같은 프로세스 안의 스레드다. 단일 VM에서 `local` 백엔드는 동작한다.

### 화보 생성이 "안 되던" 진짜 이유

DB 저장도 AI 호출도 고장난 게 아니었다. **이미지 생성 코드가 레포에 한 줄도 없었다.** `LOOKBOOK_FAKE_AI=True`가 8초 자고 고정 URL을 돌려주고 있었고, 그 `placeholder.png`조차 존재하지 않아 완료 화면에서 이미지가 깨졌다.

`_generate()`를 실구현했다. `openai` SDK를 1.59.6 → 3.3.0으로 올려야 했다 — 구 버전 `images.edit`는 이미지 1장 + 정사각형만 받아 **레퍼런스를 붙일 수 없다**. 챗봇의 `chat.completions` 호출부는 그대로 동작함을 확인했다.

마스크 규약이 이 작업의 함정이다. OpenAI는 **투명한 영역을 고쳐 그린다.** 인물을 보존하려면 인물이 불투명해야 하므로, 프론트(MediaPipe) 실루엣의 밝기를 알파로 옮긴다. 뒤집히면 얼굴만 새로 그려진다 — 극성이 반대로 올 경우를 대비해 `LOOKBOOK_MASK_INVERT`를 남겼다.

레퍼런스가 없으면 **레퍼런스 문장을 아예 넣지 않는다.** "레퍼런스를 따르라"고 써놓고 그림을 안 주면 모델이 없는 것을 상상해 구도가 튄다. 재생성은 구도·자세만 흔들고 무드는 `mood_payload`의 박제값이라 유지된다.

### CSV 60개 → demo.json

CSV에는 전시존 정보도 분석 축도 없다. 별도로 받은 "60개 목록" PDF가 `전시존-상품` 번호를 갖고 있었고, **CSV 행 순서와 1:1로 맞는 것을 8개 항목(ECONYL 소재, della robbia blue, 38/40 IT 사이즈, cognac 3건)으로 교차 검증**한 뒤 그대로 썼다. `cutout_image`가 `1~60-Photoroom.png` 순번인 것도 같은 순서를 가리킨다.

분석 축 8개는 이름·소재·가격에서 규칙으로 뽑는다. 규칙을 `import_products_csv` 한 곳에 모은 이유는 **"왜 이 상품이 미니멀인가"를 나중에 되짚기 위해서다.**

여기서 한국어 부분문자열 함정을 밟았다. `"카드" in name`으로 지갑을 판정했더니 **"로레토스 자카드 스카프"가 지갑이 됐다.** 낱말을 통째로 보도록 고쳤다.

색상은 CSV에 12종인데 축은 9종이라 가장 가까운 값으로 접는다(blue→navy, gold→metallic). 원본 색상명은 `attributes.color`에 그대로 남긴다 — 집계용 축은 거칠어도 되지만 **챗봇이 "무슨 색이야?"에 답할 때 필요한 건 "lotus pink"** 라는 앞선 교훈 그대로다. green(khaki moss) 1건만 마땅한 값이 없어 beige로 접었다.

id는 기존 DB 체계(`p_{전시존}{순번}`)를 그대로 따랐다. 처음에 전역 순번(`p_101~p_160`)으로 매겼다가 **기존 행을 갱신하지 못하고 51개가 새로 생겼다.** 로컬에서만 벌어진 일이라 정리했지만, 운영에서 그랬으면 진열대마다 옛 상품이 섞여 보였을 것이다.
